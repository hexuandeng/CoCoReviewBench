# Abstract

Personalization in Federated Learning (FL) aims to modify a collaboratively trained global model according to each client. Current approaches to personalization in FL are at a coarse granularity, i.e. all the input instances of a client use the same personalized model. This ignores the fact that some instances are more accurately handled by the global model due to better generalizability. To address this challenge, this work proposes Flow, a fine-grained stateless personalized FL approach. Flow creates dynamic personalized models by learning a routing mechanism that determines whether an input instance prefers the local parameters or its global counterpart. Thus, Flow introduces per-instance routing in addition to leveraging per-client personalization to improve accuracies at each client. Further, Flow is stateless which makes it unnecessary for a client to retain its personalized state across FL rounds. This makes Flow practical for large-scale FL settings and friendly to newly joined clients. Evaluations on Stackoverflow, Reddit, and EMNIST datasets demonstrate the superiority in prediction accuracy of Flow over state-of-the-art non-personalized and only per-client personalized approaches to FL.

# 1 Introduction

Federated Learning (FL) is a distributed machine learning paradigm where clients with resource-constrained edge devices collaboratively train a global machine learning model. In FL, each client updates a local copy of the global model weights using its local data, and sends updated weights back to a server. The server aggregates the weights and updates the global model. FL is beneficial for clients who do not have computational resources or the amount of data needed to train a model locally. However, it suffers from a well-known statistical heterogeneity issue: clients whose data distribution is different from the global data distribution wouldn't have performance incentives to participate in FL training due to the arbitrarily bad prediction performance of the global model on their data (Kairouz et al. 2021; Tan et al. 2022; Fallah, Mokhtari, and Ozdaglar 2020).

Personalization has been studied (Tan et al. 2022; Fallah, Mokhtari, and Ozdaglar 2020; Arivazhagan et al. 2019) to incentivize statistically heterogeneous clients through improved prediction performance. Typically, a client trains the global model  $\pmb{w}^g$  and a personalized model  $\pmb{w}^p$ , sending  $\pmb{w}^g$

Clients use the personalized model  $\boldsymbol{w}^p$  instead of the global model  $\boldsymbol{w}^g$  for prediction. Recent literature consistently demonstrate that personalized models can achieve higher prediction performance than the global model aggregated over clients (Fallah, Mokhtari, and Ozdaglar 2020; Deng, Kamani, and Mahdavi 2020; Liang et al. 2019; Collins et al. 2021; Pillutla et al. 2022; Li et al. 2020). Since these approaches create a personalized model specific to each client's data distribution, we refer to them as per-client personalization.

Although a personalized model can achieve statistically higher accuracy than the global model, there are still some input instances of a client that prefer to use the global model  $\boldsymbol{w}^g$  instead of the personalized model  $\boldsymbol{w}^p$ . We use per-client approaches, including APFL (Deng, Kamani, and Mahdavi 2020), Ditto (Li et al. 2021), LGFedAvg (Liang et al. 2019),

FedRecon (Singhal et al. 2021), to train global and personalized models with 100K number of clients on Stackoverflow (Federated 2022b) dataset. Our experiments show that personalized models achieve  $0.5\%$  to  $3.3\%$  higher prediction performance than a global model averaged over all clients. However, the global model still outperforms the personalized model on  $21\%$  to  $43\%$  of clients. Of the remaining clients whose personalized model outperforms the global model, an average of  $22.60\%$  of the instances were correctly classified by the global model, but incorrectly classified by the personalized model. The observation reveals a major drawback of existing per-client personalization approaches – that is, each client's personalized model is a static network that cannot accommodate the heterogeneity of the local client's data instances. Every data instance on a client is forced to use the identical personalized model for prediction despite the fact that some instances could benefit from the better generalizability of the global model.

In this paper, we propose a fine-grained personalized FL framework  $Flow$  that leverages both per-instance and per-client personalization to further improve the prediction performance of personalized models. The basic idea of  $Flow$  is to create dynamic personalized models that are adaptive to not only each client's data distribution (per-client) but also each client's individual data instance (per-instance).

Figure 1 illustrates the difference between per-client and per-instance personalization. Without personalization (Figure 1a), all the clients and all the instances on a client execute the same model for prediction. With per-instance personalization only (Figure 1b), all clients share the same global model but each input instance could activate a different part of the model for a prediction. An issue with this granularity is that the same input on different clients would always produce the same output instead of a client-specific prediction. Per-client personalization (Figure 1c) has distinct personalized models for each client but all the instances on the same client use the same model. Our proposed per-client per-instance personalization (Figure 1d) allows instances on a client to flexibly choose which part of the personalized model to activate depending on a client-specific instance.

The major challenge of per-client per-instance personalization is to design a dynamic personalized model that is capable to characterize client-specific data distribution while preserving the generalizability of the global model. We address this challenge using the Dynamic Routing mechanism for both the sequential natural language-based tasks (Liu and Deng 2018) and non-sequential image-related tasks. In each FL round, a client first finetunes the global parameters to generate local parameters. Then the client trains a dynamic personalized model that integrates the global parameters, local parameters, and a routing policy. The routing policy will determine whether to use the local parameters or its global counterpart for each input instance.

Flow has two major advantages over many existing personalization approaches. First, Flow leverages instance-level personalization to reconcile the conflicting goal between the clients and the server: an individual client wants improved prediction accuracy on its own dataset while the server wants improved generalizability of the global model

(measured usually by averaged prediction accuracy across many clients). The dynamic personalized model of  $Flow$  can achieve a better prediction performance on each client and the global model offers a good starting point for any new client to personalize from. Second,  $Flow$  is designed to be stateless because a client does not have to carry its personalized model across FL rounds (Wu et al. 2022; Singhal et al. 2021). Being stateless brings two benefits. (1) Clients who don't participate in training frequently won't suffer from stale states and thus poor accuracy. Being stateless makes it easy to scale FL training to more than thousands of clients. (2) Newly joined clients who did not participate in training before could still pull the global model, personalize it, and perform inference.

Our evaluation on cross-device language and vision tasks shows that Flow outperforms both per-client stateful and stateless personalization approaches. For the newly joined clients, Flow achieves  $0.90\%$ ,  $2.38\%$ ,  $1.26\%$  (Stackoverflow),  $0.47\%$ ,  $0.77\%$ ,  $0.51\%$  (Reddit) and  $1.08\%$ ,  $1.54\%$ ,  $2.67\%$  (EMNIST) better accuracy against its best performing stateless, stateful, and a server-side adaptive optimization baselines respectively.

Overall, this paper makes the following contributions:

- It proposes a per-client per-instance personalization framework to improve clients' accuracy in FL. It is the first work on fine-grained personalization.  
- It uses dynamic routing to achieve the finer-grained personalization, which strikes a balance between performance of the personalized model and the generalizability of the global model.  
- Our evaluation on language and vision tasks using dynamic routing shows lower instance misclassification rate for Flow over state-of-the-art personalization and general FL approaches. Compared to stateful personalization approaches, we consume fewer system resources.

# 2 Related Work

Per-Client Personalization Personalization in Federated Learning (FL) has been explored for both vision and language tasks, on the client-level granularity. APFL (Deng, Kamani, and Mahdavi 2020) interpolates a client-specific personalized model state with the global model sent by the server. Regularization is another popular way of creating a personalized model. It encourages a personalized model of each client to be close to the global model (Li et al. 2021; Dinh, Tran, and Nguyen 2020). Fine-tuning partial or entire global model to get the personalized model has been studied in (Collins et al. 2021; Pillutla et al. 2022; Yu, Bagdasaryan, and Shmatikov 2020). Multi-task learning has been utilized in (Yu, Bagdasaryan, and Shmatikov 2020; Marfoq et al. 2021; Smith et al. 2017; Dinh et al. 2021). Knowledge Distillation that enforces the similarity between logits of the global and the personalized model is investigated in (Yu, Bagdasaryan, and Shmatikov 2020; Zhang et al. 2021). Learning personalized representations of the global model has been explored in (Liang et al. 2019), and (Shamsian et al. 2021) trains a central hypernetwork model which is trained to generate a personalized

model for each client. While Ditto (Li et al. 2021), FedRep (Collins et al. 2021), Local Adaptation (Yu, Bagdasaryan, and Shmatikov 2020) have experiments on language tasks, most of the works we discussed above focus more on vision tasks. Our work gives a specific design for language tasks, along with a more general design for feed-forward networks. Besides, none of the above work has explored instance-level personalization. Since Flow is a client-side personalization approach. It can work with any other server-side optimization methods like FedAvg and FedYogi. For other personalization methods, composability would depend on whether a method can derive a local model which can be incorporated in the dynamic personalized model description provided in section C.

Stateless Personalization Personalization approaches fall into two categories: stateless and stateful. In stateful personalization, clients need to carry personalized states across FL rounds (Deng, Kamani, and Mahdavi 2020; Collins et al. 2021; Li et al. 2021; Karimireddy et al. 2020). It is not practical for large-scale FL since a client cannot participate in every FL round to keep their personalization states from getting stale. This motivates several recent works to design stateless personalization approaches such as FedRecon (Singhal et al. 2021), and LGFedAvg (Liang et al. 2019). Specifically, FedRecon (Singhal et al. 2021) creates personalized models by personalizing out-of-vocabulary tokens for each client from the global model. LGFedAvg (Liang et al. 2019) divides a model into two halves, where the feature representation half is unique for each client, and the classifier half is shared among all the clients. Flow is also designed to be stateless but features per-instance personalization to improve clients' accuracy.

Dynamic Routing Motivated by saving computational effort for "easy to predict" instances, instance-level dynamic routing has been a matter discussion in works related to early exiting (Teerapittayanon, McDanel, and Kung 2017; Bolukbasi et al. 2017; Huang et al. 2018), layer skipping (Wang et al. 2018), and multi-branching (Dai, Kong, and Guo 2020; Liu and Deng 2018). SkimRNN (Seo et al. 2018) explored temporal dynamic routing where depending on the input instance, a trained policy can determine whether to skim through the instance with a smaller RNN layer (which just updates the hidden states partially), or read the instance with a standard (bigger) RNN layer (updating the entire hidden state). Our work is motivated by the question of which route to pick, depending on its utility?, which can be achieved by using a routing policy to dynamically pick from two versions of encoders, which are equivalent in terms of computational cost but different in terms of the data they are trained on.

These local parameters will be used to initialized a dynamic personalized model in the second stage. Flow derives local parameters at the beginning of each FL round and discarding them if they are no longer needed for inference in that round. This ensures that Flow is stateless.

Flow derives local parameters  $\boldsymbol{w}^{\ell} \gets \{\boldsymbol{w}_{\mathrm{enc}}^{g}\}$  by finetuning only the encoder parameters  $\boldsymbol{w}_{\mathrm{enc}}^{g}$  on each client's local data. The rest of the global model parameters is kept frozen. The rationale is to finetune relatively small amount of parameters to reduce training time. # Stage 2: Per-Instance Personalization

Per-instance personalization allows an instance to flexibly select whether to use global parameters or local parameters to maximize prediction performance. Thus, a dynamic personalized model includes both local parameters  $\boldsymbol{w}^{\ell}$ , the global parameters  $\boldsymbol{w}^{g}$ , and also a routing policy component that determines the forward pass branch for an input.

The challenge in training such a dynamic personalized model on each client is to reconcile the conflicting goal of an individual client and the server. Some clients would prefer to always use local parameters since local parameters are already fine-tuned locally and could yield better accuracy statistically. On the contrary, the server would prefer participating clients to collaboratively update the global model parameters to improve its generalizability.

We use a two-pronged approach to address the issue. On one hand, we adopt the temperature softmax function (Hinton et al. 2015) in the routing policy component to allow soft decisions on which route to take, ensuring that global parameters always get involved in the training. On the other hand, we add to the loss function a regularization term that encourages instances to select global parameters. Below we discuss the design of dynamic routing for recurrent architectures and non-recurrent ones separately because the availability of an input instance are different for the two architectures.

Dynamic Routing for Recurrent Networks. An input instance for sequential tasks such as next word prediction is only available gradually. So a new routing decision has to be made in every timestep when a new token in the input instance is available, in order to predict the next token.

Mathematically, our routing policy is parameterized with  $\theta$ , where  $\theta_{\mathbf{w}} \in \mathbb{R}^{2 \times n}$  are weights and  $\theta_{\mathbf{b}} \in \mathbb{R}^2$  are biases. Let an input be  $\mathbf{x} = \mathbf{x}_1, \dots, \mathbf{x}_T$ , where each  $\mathbf{x}_t \in \mathbb{R}^m$  represents a token available at timestep  $t$  and  $m$  is the embedding dimension. Let previous timestep's hidden state be  $\mathbf{h}_{t-1} \in \mathbb{R}^d$ , where  $d$  is the hidden state dimension.

The routing policy has to pick one of the two routes  $(\boldsymbol{w}_{\mathrm{enc}}^{\ell}$  and  $\boldsymbol{w}_{\mathrm{enc}}^{g}$ ). The probability distribution of picking these routes for the recurrent networks is,

$$
\mathbf {r} _ {t} = \operatorname {s o f t m a x} _ {\tau} \left(\theta_ {\boldsymbol {w}} \left[ \mathbf {x} _ {t}; \mathbf {h} _ {t - 1} \right] + \theta_ {\mathbf {b}}\right) \in \mathbb {R} ^ {2}, \tag {1}
$$

where  $\tau$  is the temperature parameter of the softmax function. Lower  $\tau$  (below 1) means the policy is more confident in its choice between  $w_{\mathrm{enc}}^{\ell}$  and  $w_{\mathrm{enc}}^{g}$ , higher  $\tau$  (above 1) means the policy is less confident in its choice. We tune  $\tau$  as a hyperparameter.

The hidden state after the timestep  $t$  is the weighted average of the output from the encoder that uses global parameters and the encoder that uses local parameters:

$$
\mathbf {h} _ {t} = r _ {t} ^ {1} \times f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {g}} \left(\mathbf {h} _ {t - 1}, \mathbf {x} _ {t}\right) + r _ {t} ^ {2} \times f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {\ell}} \left(\mathbf {h} _ {t - 1}, \mathbf {x} _ {t}\right), \tag {2}
$$

where  $f_{\boldsymbol{w}_{\mathrm{enc}}^g}$  and  $f_{\boldsymbol{w}_{\mathrm{enc}}^\ell}$  are global and local encoders respectively and  $\mathbf{r}_t = [r_t^1, r_t^2]$ . The objectives of training the routing policy parameters  $\theta$ , and the global parameters  $\boldsymbol{w}^g$  are:

$$
\min  _ {\{\theta , \boldsymbol {w} ^ {g} \}} \frac {1}{N T} \sum_ {i = 1} ^ {N} \sum_ {j = 1} ^ {T} \left[ \mathcal {L} \left(f _ {\boldsymbol {w} ^ {p}} \left(x _ {i j}\right), y _ {i j}\right) - \gamma \log \left(r _ {i j} ^ {1}\right) \right], \tag {3}
$$

where  $N$  is the number of instances of a particular client, and  $T$  is the maximum sequence length, and  $\gamma$  is a regularizing hyperparameter. Note that  $i$  indexes an instance, and  $j$  indexes a token at timestep  $j$  of that instance.

Dynamic Routing for Non-Recurrent Networks. As an input instance for non-recurrent networks is typically available before the execution of the models, the dynamic routing can be simplified to be a one-time decision making process. Specifically, for the routing policy parameters  $\theta_{\mathbf{w}} \in \mathbb{R}^{2 \times n}$ ,  $n$  is the dimension of the flattened input vector,  $\mathbf{x} \in \mathbb{R}^n$ . The global and local route probabilities will be calculated as follows,

$$
\mathbf {r} = \operatorname {s o f t m a x} _ {\tau} \left(\theta_ {\boldsymbol {w}} [ \mathbf {x} ] + \theta_ {\mathbf {b}}\right) \in \mathbb {R} ^ {q}. \tag {4}
$$

The encoder outputs are the weighted average:

$$
\mathbf {x} _ {\text {i n t e r m e d i a t e}} = r ^ {1} \times f _ {\boldsymbol {w} _ {\text {e n c}} ^ {g}} (\mathbf {x}) + r ^ {2} \times f _ {\boldsymbol {w} _ {\text {e n c}} ^ {\ell}} (\mathbf {x}). \tag {5}
$$

The intermediate input  $\mathbf{x}_{\mathrm{intermediate}}$  will be fed to the decoder  $w_{\mathrm{dec}}^g$  to generate the predicted outputs for each instance. The routing policy and global objectives are similar to Equation 3 with  $T$  being always 1, as there's no concept of sequence length for non-sequential tasks.

# Pre-Inference Processing and Inference

A client has to create its dynamic personalized model before inference. It is achieved by procedure CLIENTPREINFERENCE which is identical to CLIENTTRAIN in Algorithm 1, except that we drop the  $\boldsymbol{w}^g$  update in Line 22. It trains the local parameters  $\boldsymbol{w}^\ell$  and the routing policy  $\theta$  following similar steps as in training, with its training dataset. Specifically, a client (1) pulls the latest global model  $\boldsymbol{w}^g$ , (2) initializes and trains  $\boldsymbol{w}^\ell \gets \{\boldsymbol{w}_{\mathrm{enc}}^g\}$  with  $\mathcal{D}_\ell$  which is a split of the training dataset, and (3) initializes and trains the routing policy  $\theta$  based on  $\boldsymbol{w}^p \gets \{\boldsymbol{w}^g, \boldsymbol{w}^\ell, \theta\}$  with  $\mathcal{D}_g$ , the other split.

After pre-inference processing, a client uses  $\boldsymbol{w}^p$  for inference. To make inference as efficient as the per-client personalization algorithms, the dynamic personalized model will make "hard" decisions during inference – only the updates from one of the local and global routes are used for an input instance of a timestep.

For recurrent networks, the hidden state update for timestep  $t$  would be as follows,

$$
\mathbf {h} _ {t} = \left\{ \begin{array}{l l} f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {g}} \left(\mathbf {h} _ {t - 1}, \mathbf {x} _ {t}\right) & \text {i f} r _ {t} ^ {1} > 0. 5, \\ f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {\ell}} \left(\mathbf {h} _ {t - 1}, \mathbf {x} _ {t}\right) & \text {o t h e r w i s e .} \end{array} \right. \tag {6}
$$

For non-recurrent networks, the intermediate input update for would be as follows,

$$
\mathbf {x} _ {\text {i n t e r m e d i a t e}} = \left\{ \begin{array}{l l} f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {g}} (\mathbf {x}) & \text {i f} r ^ {1} > 0. 5, \\ f _ {\boldsymbol {w} _ {\mathrm {e n c}} ^ {\ell}} (\mathbf {x}) & \text {o t h e r w i s e .} \end{array} \right. \tag {7}
$$

In Flow, each client only needs to send (fetch) the global model parameters back to (from) the server. The amount of communication is  $O(\boldsymbol{w}^g)$ . There's no additional communication overhead compared to FedAvg (McMahan et al. 2017). More details on resource usage are in Appendix B.

# 4 Evaluations

We validate Flow by analyzing its empirical performance against various per-client personalization approaches, both stateful and stateless, as well as general FL approaches without client-side personalization.

# Experiment Settings

Models and Datasets We target two next-word prediction tasks using datasets, Stackoverflow (Federated 2022b) and Reddit (BigQuery 2022), and one image classification task using EMNIST (Federated 2022a). Details on dataset heterogeneity are available in Appendix C. For Stackoverflow, we use the same LSTM model (1 layer LSTM followed by 2 fully connected layers) as in (Reddi et al. 2021). For Reddit, we use the LSTM model (2 stacked LSTM layers followed

by a fully connected layer) as in (McMahan et al. 2018). For EMNIST, we used the recommended 2 layer CNN model in (Reddi et al. 2021). The detailed hyperparameter settings are available in Appendix C.

Baselines We compared Flow against the following baselines: three no personalization approaches (FedAvg (McMahan et al. 2016), FedProx (Li et al. 2020), and FedYogi (Reddi et al. 2021)), two stateful per-client personalization approaches (APFL (Deng, Kamani, and Mahdavi 2020) and Ditto (Li et al. 2021)), two stateless per-client personalization approaches (LGFedAvg (Liang et al. 2019), and FedRecon (Singhal et al. 2021)). Descriptions of each of these baselines are given in Section 2. We also compare Flow with Dynamic Routing (DR) where the global model itself is a dynamic network and clients finetune it to create dynamic personalized models. The goal of this DR baseline is to show whether Flow has benefits over a simple finetuning of  $w^g$ . Note that APFL interpolates an entire global model with a personalized model by a client-specific interpolation factor  $\alpha$ , which is similar to our  $r$  with the exception that  $r$  is instance-specific, while  $\alpha$  is the same for all instances.

All the baselines and Flow use the same train/validation/test data split. For the train split, only FedRecon and Flow further separate the "train split" into two sets: (1)  $\mathcal{D}_{\ell}$ , which will be the former half of all the input sequences, (2)  $\mathcal{D}_g$ , which will be the latter half of the same input sequences. This is in line with how datasets are split in (Singhal et al. 2021). Vertical splits like this ensures that all the input sequences contribute to both local and global training. Since there's no notion of sequentiality in image classification tasks, we split the training dataset in two equal halves to derive  $\mathcal{D}_{\ell}$  and  $\mathcal{D}_g$ . Flow uses  $\mathcal{D}_l$  to train local models and  $\mathcal{D}_g$  to train the routing policy and global model. FedRecon uses  $\mathcal{D}_l$  to reconstruct some local parameters and  $\mathcal{D}_g$  to train global models. The validation and test dataset splits are the exact same for all the baselines.

Evaluation Metrics Prediction performance is evaluated by both validation accuracy and test accuracy. Validation accuracy reported in Figure 3 is calculated by averaging per-round accuracies over the range of 100 rounds. Test accuracy, as shown in Table 1, is calculated at the end of the federated training for additional 100 rounds, picking test clients at random, and then averaging accuracies of all 100 rounds. For both validation and testing, we have used 100 clients for Stackoverflow, 10 clients for both Reddit, and EMNIST (this count is the same for training client count per round). The clients are randomly picked from a cohort of 204,088 (Stackoverflow), 157,572 (Reddit), and 3400 (EMNIST) clients available for testing.

Since many wouldn't have participated once or more than once during the training, we consider those as newly joined clients during inference. Both for validation and test accuracies, clients first have to derive  $\boldsymbol{w}^p$  based on CLIENTPREINFERENCE procedure, then use that  $\boldsymbol{w}^p$  for inference. Since the inference is on  $\boldsymbol{w}^p$ , we are mainly reporting the personalized accuracies for our baseline approaches, Flow, and its variants discussed in the baselines section above.

# Results and Analysis

Prediction Performance Figure 3 shows the validation accuracy of Flow and its baselines on Stackoverflow, Reddit, and EMNIST respectively. Table 1 reports the test accuracies. We make the following observations. (1) Dynamic Routing (DR) outperforms per-client personalization APFL, Ditto, and LGFedAvg, proving that instances of the same client do prefer different parts of the model. (2) As a stateless personalization approach, FedRecon (using FedYogi as aggregation) outperforms stateful approaches since the latter require training of personalized models over multiple rounds, which are impractical when only  $\sim 5 - 6\%$  of total clients would participate during FL training.

Overall, Flow outperforms all the baselines. Flow outperforms FedRecon, the best of all the baselines, by  $0.90\%$  on Stackoverflow and  $0.47\%$  on Reddit in terms of test accuracy. It is because Flow is finer-grained and dynamic in its choice of client-specific local parameters and global parameters. The results demonstrate that per-instance personalization further improves the performance of a per-client personalized model.

Importance of Per-Instance Personalization In order to show the efficacy of dynamic routing approached used by Flow, we compare Flow with two of its variants as follows: (a) Global route only: a modification of Flow where  $\mathbf{r}(\mathbf{r}_t\forall t\in [1,T]$  in case of recurrent networks) is always 1.0 for all the instances, (b) Local route only: a modification of Flow where  $\mathbf{r}(\mathbf{r}_t\forall t\in [1,T]$  in case of recurrent networks) is always 0.0 for all the instances. The first variant indicates that the policy in  $\pmb{w}^{p}$  is forced to take the global route for all the clients and their instances, while the second baseline indicates that the policy in  $\pmb{w}^{p}$  would always take the local route regardless of the clients and their instances.

Test accuracy results in Table 2 shows that per-instance routing is superior to routing designs which are not based on instances. Besides, the "local route only" variant outperforms the "global route only", which echoes the intuition that finetuning a global model can increase clients' accuracy. Note that the test accuracies reported in Table 2 are based on evaluation done after the global model is trained according to Algorithm 1. The increase in "local route only" variant displays better generalizability of the global model as compared to rest of the baselines reported in Table 1.

Table 3 shows the reduction in the number of instances which are misclassified by the personalized model, but correctly classified by the local model. This indicates that using the global model for a subset of instances would be indeed more beneficial.

Analysis on Per-Instance Routing Decisions The analysis aims to show the importance of per-instance personalization by examining the behavior of routing decisions (r). The behavior of routing decisions is closely related to the notion of heterogeneity of a certain client. To understand it, we need a measure of the level of heterogeneity within a client, with respect to the global data distribution. We use Kullback-Leibler (KL) divergence as the metric. Definitions are in Appendix E.

We picked 100 test clients with their KL divergence having mean of 5.67, median of 3.00, and the range of 0.05 to 24.63. Soft Decisions During Inference We didn't use soft decisions during inference for two reasons. First, it does not improve the accuracy of Flow much. The test accuracies for Flow on Stackoverflow and Reddit with hard decisions are  $29.16\% \pm 0.21\%$ , and  $19.36\% \pm 0.19\%$ , while with soft decisions, we observed  $29.22\% \pm 0.24\%$ , and  $19.46\% \pm 0.15\%$ . Second, using soft decisions means that both global routes and local routes have to be executed. It doubles the computation and increases the inference overhead.

Local Epoches and Regularization We notice that for language tasks, lesser number of epochs are sufficient to derive the dynamic personalized models, while image-related tasks require more epochs, as discussed further in Appendix F. Appendix F also shows that adding a regularization term improves the global model generalizability, which in turn produces more accurate dynamic personalized models.

# 5 Conclusion

We presented Flow, a fine-grained personalized federated learning (FL) approach to improve clients' accuracy. For each client, Flow creates a dynamic personalized model that leverages a dynamic routing mechanism to determine whether to use local parameters or global parameters for inference depending on the input instance. Our empirical evaluation shows that Flow achieves a better personalized performance for newly joined clients.
